# 关于lv_img_src_get_type获得图片类型的解析

```c
/**
 * Source of image.*/
enum {
    LV_IMG_SRC_VARIABLE, /** Binary/C variable*/
    LV_IMG_SRC_FILE, /** File in filesystem*/
    LV_IMG_SRC_SYMBOL, /** Symbol (@ref lv_symbol_def.h)*/
    LV_IMG_SRC_UNKNOWN, /** Unknown source*/
};

typedef uint8_t lv_img_src_t;
```



| 对比维度                   | **变量方式 (LV_IMG_SRC_VARIABLE)**                           | **文件系统方式 (LV_IMG_SRC_FILE)**                           |
| :------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **1. 存储位置**            | 烧录在 **MCU内部的Flash（闪存）** 或外部QSPI Flash中，和你的程序代码“住在一起”。 | 存储在 **文件系统设备**中（如SD卡、SPI Flash上的FATFS分区、U盘等）。 |
| **2. 读取机制**            | **零开销读取**。数据地址在编译时已确定，LVGL直接通过指针访问内存，相当于“看一眼”就有了。 | **需要驱动层介入**。LVGL必须调用文件系统API（如 `f_open`、`f_read`）去底层硬件上寻找并读取数据。 |
| **3. 读取速度**            | **极快（纳秒级）**。CPU直接寻址，通常搭配DMA直接刷屏，几乎不占用CPU等待时间。 | **较慢（毫秒级甚至更高）**。受限于SPI总线速度或SDIO速率，且需要经过文件系统的层层解析，存在IO等待。 |
| **4. 更新维护便捷性**      | **极麻烦**。图片有任何修改，都需要重新转换图片成 `.c` 文件，然后**重新编译整个工程**并重新烧录固件。 | **极方便**。只需要把新的图片文件（如 `new_image.png`）复制到SD卡或U盘里覆盖旧文件即可，**无需重刷固件**。 |
| **5. 对内存（RAM）的占用** | 数据常驻 **Flash（ROM）**，显示时通常只需要极小的缓冲Buffer（如单行Buffer），**几乎不额外占用RAM**。 | 数据在外部存储，读取时通常需要申请一块**较大的RAM动态缓冲区**来存放解码后的像素，或者分块加载，RAM开销较大。 |
