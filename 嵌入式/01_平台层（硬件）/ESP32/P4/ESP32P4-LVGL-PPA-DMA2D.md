# ESP32-P4 MIPI 屏幕驱动与 LVGL 渲染笔记

## 1. 前提与场景
- ESP32-P4 通过 MIPI DSI 驱动屏幕。
- LVGL 渲染出最终 UI 后直接显示到屏幕。
- 屏幕端**不进行硬件图层混合**。
- PPA 仅负责将 LVGL 输出的 `ARGB8888` 转换为 `RGB888`（或 `RGB565`）。

## 2. 像素格式选择：ARGB8888 vs RGB888 vs XRGB8888

| 格式         | 位宽  | Alpha 语义                  | 内存/带宽              | 对齐                       | 适用性                           |
| ------------ | ----- | --------------------------- | ---------------------- | -------------------------- | -------------------------------- |
| **ARGB8888** | 32 位 | 有效 Alpha，可半透明        | 高（比 RGB888 多 33%） | 32 位对齐，CPU 友好        | 需要硬件 BLEND 时才有意义        |
| **XRGB8888** | 32 位 | Alpha 被忽略，通常固定 0xFF | 与 ARGB8888 相同       | 32 位对齐，CPU 友好        | LVGL 32 位默认，无混合需求时可用 |
| **RGB888**   | 24 位 | 无 Alpha                    | 最低                   | 非 32 位对齐，访问可能跨字 | 带宽敏感、无混合需求时最优       |

- **32 位对齐的理论优势**：ARGB8888 单次内存访问即可读写一个像素，避免 RGB888 的非对齐惩罚。
- **ESP32-P4 现实限制**：
  - DMA2D **不支持 ARGB8888 作为输入格式**。
  - MIPI DSI 控制器处理 RGB888 DMA 缓冲区可能存在限制。
  - PPA 内部常以 ARGB8888 为中间格式。
- **结论**：在“LVGL 自行混合 + PPA 仅 SRM + 屏幕无混合”场景下，**RGB888 或 XRGB8888 比 ARGB8888 更合适**。首选 RGB888（省带宽），次选 XRGB8888（对齐好但带宽同 ARGB）。避免 ARGB8888，除非后续有硬件 BLEND 需求。

## 3. Alpha 与透明度：LVGL 混合机制
- **ARGB 顺序**：`0xAARRGGBB`。
  - `0x7f0000ff` = A=0x7f, R=0, G=0, B=0xff → **半透明纯蓝色**。
  - `0xff00007f` = A=0xff, R=0, G=0, B=0x7f → **不透明暗蓝色**（不是淡蓝）。
- **屏幕不做混合时**：Alpha 通道被忽略，`0x7f0000ff` 显示为纯蓝，`0xff00007f` 显示为暗蓝。
- **LVGL 的透明效果**：
  - LVGL 软件渲染器**始终在 CPU 中执行 Alpha 混合**。
  - 若背景在同一帧缓冲内：LVGL 读取背景色，与前景按 Alpha 混合，写入**不透明的最终 RGB 结果**。
  - 若背景来自外部（如视频层）：LVGL 无法混合，会保留原始 Alpha，期望硬件 BLEND 处理。
- **关键点**：混合要么由 LVGL 在渲染时完成（输出不透明 RGB），要么由 PPA 的 BLEND 硬件完成（输入 ARGB，硬件混合后输出 RGB）。不能依赖 SRM 的“格式转换”来弥补。

## 4. PPA 模式：SRM vs BLEND
- **SRM（缩放-旋转-镜像）**：
  - 负责几何变换和格式转换。
  - 输入 ARGB8888、输出 RGB888 时，**丢弃 Alpha，不改变 RGB 分量**。
  - 可通过寄存器修改 Alpha 本身，但不影响 RGB。
  - 你的场景（PPA 仅做 ARGB→RGB 转换）属于 **SRM 模式**。
- **BLEND（混合）**：
  - 用于图层叠加，Alpha 值**直接参与混合计算**，改变最终 RGB 输出。
  - 公式：`Cout = (Cb × Ab × (1 - Af) + Cf × Af) / (Ab + Af - Ab × Af)`。
  - 支持 Color Key 透明色机制。
- **结论**：SRM 下 Alpha 被丢弃，RGB 不变；BLEND 下 Alpha 影响 RGB。

## 5. PPA 加速 LVGL 渲染
- **启用方式**：
  - `CONFIG_LV_USE_PPA=y`
  - `CONFIG_LV_DRAW_BUF_ALIGN=64`（对齐到 64 字节缓存行）
- **性能收益**：
  - 填充（Fill）和矩形拷贝提升显著，平均节省约 30% 渲染时间，填充场景可达 9 倍加速。
  - 图像混合（Blend）收益有限，受 DMA2D 内存带宽瓶颈限制。
  - 局部刷新（Partial Mode）下 PPA 无增益，推荐配合**双缓冲（Double Buffer）**。
- **限制与问题**：
  - 实验性阶段，可能出现 DSI 欠载（Underrun）、画面撕裂。
  - 缓解：降低 PPA 突发传输长度（128→64 字节）、PSRAM 速度设为 200MHz。
  - 硬件要求：缓冲区地址和大小需 64 字节 L2 缓存行对齐。

## 6. 硬件 vs 软件问题与 ESP-IDF 优化
- **硬件根本限制**：
  - DMA2D 内存带宽瓶颈。
  - PSRAM 带宽硬约束（如 1280x720x16bit@60Hz 仅 DSI 读取就需 111MB/s）。
  - 64 字节缓存行对齐要求。
- **软件成熟度问题**：
  - PPA 队列时序、缓冲区同步、脏区域重绘错误。
  - 可通过 ESP-IDF 更新修复。
- **优化建议**：
  - 升级到 **ESP-IDF v5.5.2+** 或 v6.0.1。
  - `CONFIG_SPIRAM_SPEED_200M=y`。
  - 降低 PPA 突发长度至 64 字节。
  - 保持 LVGL 更新，获取 PPA 同步与缓存修复。
  - 合理预期：PPA 优势在**大块矩形填充**，混合操作受限。

## 7. 推荐配置：RGB888 + PPA + DMA2D
- **可行且推荐**：使用 RGB888 作为 LVGL 渲染结果格式，同时启用 PPA 加速。
- **PPA 原生支持 RGB888**：SRM 和 BLEND 均支持 RGB888 输入/输出。
- **收益**：
  - 填充操作帧率提升明显。
  - 混合操作收益有限（受 DMA2D 带宽限制）。
- **配置要点**：
  - `CONFIG_LV_USE_PPA=y`
  - `CONFIG_LV_DRAW_BUF_ALIGN=64`
  - BSP 颜色格式设为 `CONFIG_BSP_LCD_COLOR_FORMAT_RGB888`
  - 配合双缓冲使用，减少 DSI 欠载风险。

## 8. DMA2D 的作用
在“RGB888 + PPA 加速”配置下，DMA2D 是**不可或缺的协同伙伴**：

1. **PPA 的专属数据搬运引擎**：
   - 将待处理数据搬入 PPA。
   - 将 PPA 处理结果搬出到目标缓冲区。
   - PPA 负责“算”，DMA2D 负责“搬”。

2. **显示刷新与防撕裂**：
   - 将渲染完成的缓冲区内容高效拷贝到 MIPI DSI 帧缓冲区。
   - 通过 `CONFIG_BSP_DISPLAY_LVGL_AVOID_TEAR` 配合双缓冲实现无撕裂显示。

3. **独立能力**：
   - 异步色彩格式转换（YUV ↔ RGB）。
   - 2D 数据块拷贝（内存到内存，支持窗口区域）。

**协同工作流**：
LVGL 渲染 → DMA2D 搬入 PPA → PPA 处理 → DMA2D 搬出 → DMA2D 刷新到 MIPI DSI → 屏幕显示。

## 9. 关键结论速查
- 无硬件混合时，**RGB888 或 XRGB8888 优于 ARGB8888**。
- ARGB8888 的 Alpha 在 SRM 模式下被丢弃，不改变 RGB；在 BLEND 模式下参与混合并改变 RGB。
- LVGL 的透明效果通过**软件混合**在渲染阶段完成，输出不透明 RGB 到帧缓冲。
- 启用 PPA 加速可显著提升填充类操作，混合类操作受 DMA2D 带宽限制。
- 推荐配置：**LVGL 输出 RGB888 + PPA 加速 + DMA2D 搬运 + 双缓冲显示**。
- 硬件瓶颈（DMA2D/PSRAM 带宽、64 字节对齐）无法通过软件完全消除；软件问题可通过更新 ESP-IDF 和 LVGL 缓解。
