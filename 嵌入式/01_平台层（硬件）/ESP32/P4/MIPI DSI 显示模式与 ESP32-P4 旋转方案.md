# MIPI DSI 显示模式与 ESP32-P4 旋转方案

## MIPI DSI 的两种数据传输模式

**Command 模式（命令模式 / DBI）**
- 主机把图像写入面板自带的 GRAM，面板自己从 GRAM 刷新屏幕
- 面板必须带 GRAM，接口是双向的
- 因为写的是 GRAM，主机可以通过 MADCTL 命令改变写入顺序（行列交换），硬件旋转可行
- 功耗低，刷新率受 GRAM 写入速度限制

**Video 模式（视频模式 / DPI）**

- 主机持续把像素流实时发给面板，和面板 VSync 严格同步
- 面板不需要 GRAM，接口可以是单向的
- 数据流顺序由 DSI 控制器硬件固定，面板被动接收，硬件旋转不可行
- 支持高分辨率高刷新率，适合视频播放，但主机必须持续工作

**对比**

| 特性      | Command 模式 (DBI) | Video 模式 (DPI)  |
| :-------- | :----------------- | :---------------- |
| 数据流向  | 主机 → 面板 GRAM   | 主机 → 面板实时流 |
| 面板 GRAM | 必需               | 不需要            |
| 硬件旋转  | 支持               | 不支持            |
| 典型场景  | 静态显示、低功耗   | 高刷、视频播放    |

## ESP32-P4 的硬件设计选择

乐鑫官方文档和技术百科都明确说明：**ESP32-P4 的 MIPI DSI 仅支持 Video 模式输出视频流，不支持 Command 模式**。

在这套架构里，DBI 只被用作“控制通道”，负责发初始化命令和寄存器配置，不传视频像素数据。视频帧数据只走 DPI 通道。Zephyr 的驱动代码里也做了强制检查，非 Video 模式直接报“Only video mode is supported”并返回不支持。

**这不是硬件缺陷，而是架构设计取舍**。Video 模式面向高分辨率、高刷新率的视频流传输，通过省略面板 GRAM 来简化屏幕设计、提升效率。代价就是放弃了 Command 模式下的硬件旋转能力。

## Video 模式下显示方向固定的原因

- Video 模式下，DSI 控制器按固定像素时钟把帧缓冲数据发出去，扫描顺序由硬件时序决定，运行时改不了
- JD9366 的 MADCTL 里负责行列交换的位，只在 Command 模式下控制 GRAM 写入顺序，Video 模式下数据不经过 GRAM，这个位不生效
- 驱动层也因此禁用了 `swap_xy`，因为底层硬件没有对应的能力
- 帧缓冲的 DMA 布局是按面板原生分辨率和行步长对齐的，强行改方向会破坏对齐，触发内存异常

## 解决方案

### PPA 硬件加速（推荐）

PPA（Pixel Processing Accelerator）是 ESP32-P4 内置的 2D 图像处理硬件加速器，用于在硬件层面实现图像旋转、缩放、镜像和混合等操作。

**架构与工作原理**

PPA 并非独立工作，而是与 DMA2D（2D DMA）硬件协同。DMA2D 负责在系统内存和 PPA 处理引擎之间搬运输入/输出缓冲数据，PPA 核心则执行实际的图像算法加速。在 ESP32-P4 中，只有 JPEG 编解码器和 PPA 支持 2D-DMA，两者共享同一套 2D-DMA 控制器和内存地址空间。

PPA 支持三种操作类型：SRM（缩放-旋转-镜像）、叠加（Blend）和填充（Fill）。其中 SRM 操作可直接完成 90°/180°/270° 旋转和镜像，这正是显示旋转所需的硬件路径。

**性能数据**

根据 LVGL 官方基准测试，启用 PPA 后：

- 图像和矩形填充绘制任务平均节省约 30% 的渲染时间，在显示尺寸整数倍的纯填充场景下可达 9 倍加速。
- 相比纯软件旋转，使用 PPA 旋转平均节省高达 40% 的渲染时间，且 CPU 全程保持空闲，可用于处理视频解码、网络通信等其他任务。
- PPA 旋转是异步操作，不阻塞 CPU 执行后续指令。

**使用方式**

PPA 相关配置通过 `idf.py menuconfig` 菜单开启，具体路径在 LVGL 与显示相关的配置项中。进入菜单后启用 PPA 绘制单元，保存退出，重新编译即可。PPA 代码会自动编译并运行，应用代码无需任何修改。LVGL 的 ESP-IDF 显示驱动在检测到旋转/镜像标志时，会自动调用 PPA 客户端完成旋转和镜像处理，再将结果发送给显示控制器。

建议配合双缓冲模式使用，因为 PPA 在部分渲染模式下受 DMA2D 内存带宽限制，性能提升不明显。

**注意事项**

PPA 支持目前处于实验性阶段。矩形复制/填充类任务的性能增益明显，但图像混合（Blend）操作虽可正常运行，增益不显著，主因是 DMA2D 的内存带宽限制。此外，PPA 性能高度依赖 PSRAM 带宽，当图片数据位于 PSRAM 时，多个外设同时读写会显著影响 PPA 吞吐。建议使用双缓冲而非部分渲染模式，并合理规划内存布局。

### LVGL 软件旋转（备选）

LVGL 自带的旋转功能，用 CPU 逐像素处理。实现简单，但占用大量 CPU，不适合视频播放这类高性能场景，官方也评价这种方式“用全帧缓冲，不够理想”。

### DMA2D 直接搬运（实验性）

直接操作帧缓冲和 VSYNC 中断，绕开 PPA 核心，仅使用 DMA2D 硬件搬运数据。实现复杂，性能受内存带宽限制，一般不推荐。

### 方案对比

| 方案           | 实现难度       | 性能                          | CPU 占用     |
| :------------- | :------------- | :---------------------------- | :----------- |
| PPA 硬件加速   | 低（菜单配置） | 高（异步，节省 40% 渲染时间） | 极低（空闲） |
| LVGL 软件旋转  | 低             | 中（受 CPU 性能限制）         | 高           |
| DMA2D 直接搬运 | 高             | 中（受内存带宽限制）          | 低           |

## 总结

- MIPI DSI 两种模式中，只有 Command 模式支持硬件旋转
- ESP32-P4 只实现了 Video 模式，所以硬件旋转这条路走不通
- Video 模式方向固定是硬件时序和协议约束决定的，不是软件没实现
- 在 ESP32-P4 上做高性能旋转，PPA 是唯一正确的硬件路径
